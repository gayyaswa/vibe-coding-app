Stock Portfolio Risk Analyzer

Vibe Coding Project  |  June 1, 2026  |  Stack: Python · Streamlit · Pandas · Plotly

1. Project Overview

Aspect Details
What I built A Streamlit web app that loads a stock portfolio from CSV, auto-assigns each holding to one of four risk buckets (Less Risk, Moderate, Growth, Aggressive), and helps the user rebalance their portfolio to match a target allocation.
Problem solved Most portfolio trackers show what you own. This app tells you whether your current mix matches your risk appetite and exactly what to buy or sell — in dollar amounts — to fix it.
Target user Individual retail investors holding a mix of ETFs, stocks, and bond funds who want a visual, actionable view of their risk profile.
Path chosen Path B — Custom app (stock portfolio analyzer with risk bucketing and rebalancing engine, beyond the basic walkthrough demo).
Tech stack Python 3.9 · Streamlit (UI) · Pandas (data) · Plotly (charts)
App sections 1. Portfolio Overview — full holdings table with filters and P&L metrics
2. Allocation Dashboard — donut chart + target sliders with sum-to-100 validation
3. Rebalancing Engine — BUY / SELL / HOLD actions with dollar amounts
4. Sector Breakdown — grouped bar chart + sector × bucket heatmap
5. Gain/Loss Summary — P&L per ticker and per risk bucket
Tests 30 unit tests across two test files (test_categorizer.py · test_rebalancer.py). All pass.
Total portfolio value $110,139 market value · $80,960 cost basis · $29,179 unrealized gain (+36%)

4. Iterations Tried

Iteration What I Tried / Considered What Was Chosen Instead Why
Risk classification logic Sector-only rules (e.g. Technology → Growth for all tech stocks) Two-layer lookup: ticker override first, then sector rule as fallback MSTR is labeled Technology by sector but is essentially a Bitcoin proxy — sector alone misclassifies it. Ticker overrides capture asset-specific knowledge sector labels cannot.
Slider sum constraint Auto-adjust sibling sliders so the total always stays at 100% as the user drags Independent sliders + real-time sum display + warning + disabled confirm button until sum = 100 Auto-adjust causes an infinite rerun loop in Streamlit — every slider change triggers a rerun, which changes other sliders, which triggers another rerun. Manual adjustment with clear feedback is more stable and more transparent.
Rebalancing HOLD threshold Label every stock with a non-zero delta as BUY or SELL Deltas under $50 absolute value are labeled HOLD Without a threshold, floating-point math produced absurd outputs like "SELL $2.14 of MMF." A $50 floor keeps the rebalancing table actionable rather than noisy.
Delta distribution within buckets Sell the most overweight stock in a bucket first (concentrated approach) Distribute bucket delta proportionally across all stocks in that bucket by current weight Concentrated selling would deplete NVDA entirely before touching MSFT or AAPL. Proportional distribution keeps the internal composition of each bucket unchanged — only the bucket size changes. This matches how a passive investor would rebalance.
Navigation structure Multi-page app using Streamlit's pages/ folder, or st.tabs() st.sidebar.radio() with 5 sections in a single app.py Sidebar navigation matches the "dashboard" mental model for a financial app. Single-file approach shares session state (portfolio df, confirmed targets) naturally without cross-page state management complexity.

5. Learnings and Observations

Category Observation
Plan before code The most valuable moment in the workflow was entering Plan Mode before any file was created. Claude proposed the architecture, data model, rebalancing math with a worked example, and build order — all for approval before touching a file. Implementation was then fast and linear with no wasted rework.
Tests early, not after Asking for unit tests before the first standalone run changed the quality of the code. The rebalancer's HOLD threshold, proportional distribution, and sign logic were all verified immediately. It also caught a subtle edge case: the proportional weight calculation needed a guard for empty buckets (division by zero).
AI held architecture in context BUCKET_COLORS was defined once in categorizer.py and imported consistently by app.py and all chart configurations — never duplicated. Across file creation, module imports, session state design, and UI layout, Claude maintained consistency without being reminded.
Risk classification needs human judgment The ticker override table (e.g. MSTR → Aggressive despite Technology sector) reflects a human call about what those assets actually are, not just their label. Claude built the framework; domain knowledge came from the human. The AI cannot independently decide that MicroStrategy is a Bitcoin proxy.
Prompts are design decisions "Can we add unit tests?" is also "I want this code to be correct and verifiable." Every prompt in this project was a design choice disguised as a request. The AI acts on stated intent — the values behind that intent come from the human.
Iteration is cheap, direction is not Changing a chart type, adding a filter, or tweaking the HOLD threshold took seconds. Changing the fundamental structure (e.g. sidebar nav → tabs) would touch many files. The upfront planning session paid for itself by locking in the right direction early.
You must understand the math to trust it Verifying the rebalancing engine required working through the proportional distribution example on paper before trusting the output. The AI wrote correct code — but knowing it was correct required understanding the underlying math independently.
Synthetic data is a deliberate tradeoff Using a static CSV instead of a live market data API (Yahoo Finance, Alpha Vantage) removed API key complexity and made the app work offline. The tradeoff is that "current prices" are frozen. A production version would replace the CSV with a real-time data feed.
Using Claude Agent architecture to persist workflow state across sessions This project spans 3 days. To avoid re-explaining context at the start of every session, Claude Code's agent memory and CLAUDE.md were used as a two-layer persistence system:

CLAUDE.md (project-level) — auto-loaded by Claude Code at the start of every session. Contains the full architecture, iteration plan by day, coding conventions, and design decisions that must not be changed without deliberate intent.

Agent memory (user-level) — Claude's own memory system stores project state, user working style, and workflow preferences (e.g. always update prompts.md, HTML is the doc source of truth). This persists even across different machines or IDEs.

Together these mean Day 2 and Day 3 sessions begin with full context — no re-explaining the stack, the risk bucket rules, or the prompt-logging convention. The AI picks up exactly where the previous session ended.
