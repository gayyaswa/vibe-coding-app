Stock Portfolio Risk Analyzer

Vibe Coding Project  |  June 1–3, 2026  |  Stack: Python · Streamlit · Pandas · Plotly · LangChain · Anthropic  |  Days completed: 3 of 3

1. Project Overview

Aspect Details
What I built A Streamlit web app that loads a stock portfolio from CSV, auto-assigns each holding to one of four risk buckets (Less Risk, Moderate, Growth, Aggressive), and helps the user rebalance their portfolio to match a target allocation. Day 2 added a visual-first portfolio overview (treemap), portfolio health scores vs. benchmarks, a blue/grey theme, and a full architectural refactor.
Problem solved Most portfolio trackers show what you own. This app tells you whether your current mix matches your risk appetite, how it compares to standard benchmarks (Conservative, Balanced, Aggressive Growth), and exactly what to buy or sell — in dollar amounts — to fix it.
Target user Individual retail investors holding a mix of ETFs, stocks, and bond funds who want a visual, actionable view of their risk profile.
Tech stack Python 3.9 · Streamlit (UI) · Pandas (data) · Plotly (charts) · LangChain + langchain-anthropic (AI insights) · claude-sonnet-4-6
App sections Navigation: top tabs (changed from sidebar in Day 2)

1. Portfolio Overview — treemap (dominant), health score vs. 3 benchmarks, holdings detail (collapsible)
2. Allocation Dashboard — donut chart + target sliders with sum-to-100 validation
3. Rebalancing Engine — BUY / SELL / HOLD actions with dollar amounts
4. Sector Breakdown — grouped bar chart + sector × bucket heatmap
5. Gain/Loss Summary — P&L per ticker and per risk bucket
6. AI Insights — LangChain + Claude; Rebalancing Rationale + Sector Concentration; streaming token-by-token
Architecture utils/ — Pipeline, Strategy (categorizer), Facade (PortfolioFacade), Factory (HealthScoreFactory), Registry (BENCHMARK_REGISTRY)
views/ — one render() function per tab section
app.py — ~60-line router (was 306 lines Day 1)
Tests 48 unit tests across 4 test files (test_categorizer.py · test_rebalancer.py · test_health.py · test_insights.py). All pass.
Total portfolio value $110,139 market value · $80,960 cost basis · $29,179 unrealized gain (+36%)

2. Dataset Used

Sample data: data/portfolio_sample.csv — 20 synthetic holdings (5 per risk bucket) covering stocks, ETFs, and money market funds across 8 sectors. Prices are static (no live feed); this was a deliberate tradeoff to keep the app self-contained without API keys.

I proposed the $50 threshold; the AI implemented it. This taught me that AI output needs human review not just for correctness but for usefulness. I had to think about what kind of investor this app is for — passive vs. active. Proportional distribution matched the passive investor philosophy I was designing for. This was less about AI and more about me clarifying my own intent. Prompts that force a choice reveal assumptions you didn't know you had.

5. Learnings and Observations

Reflections on using Claude Code as an agentic AI tool to build this application — what shaped my thinking, what I'd do differently, what I now do by default.

Day 1 — Learning to use the tool
Category Observation
Plan before code — initial discomfort, then appreciation Entering Plan Mode before writing any code felt slow at first — I wanted to start building. But the architecture session paid for itself immediately. No wasted rework, no mid-implementation "wait, how does this connect to X?" moments. I now treat Plan Mode as a non-negotiable first step for anything touching more than a few files. The discomfort of pausing is a much smaller cost than the cost of reworking a wrong direction.
Tests as an afterthought that became a quality gate I asked for tests almost as an add-on ("can we also add unit tests?") without fully anticipating the impact. The tests caught a real bug — division by zero in the proportional weight calculation for empty buckets — that would have been a silent failure in production. I now understand why the convention in CLAUDE.md says "add tests for any new function in categorizer.py or rebalancer.py." It's not ceremony; it's a quality gate that pays back immediately.
Every prompt encodes a value judgment "Can we add unit tests?" was also "I want this code to be correct and verifiable." I didn't consciously frame it that way, but reflecting back, every prompt I wrote encoded a value: correctness, usability, maintainability, structure. The AI acts on stated intent — the values behind that intent come from me. Being deliberate about what I'm asking for is the same as being deliberate about what I'm building.
Domain knowledge is the irreplaceable human contribution The AI built the classification framework. I supplied the overrides — MSTR is a Bitcoin proxy, COIN is speculative finance, JNJ is a stable blue-chip despite being in Healthcare. None of these calls come from sector labels; they come from understanding what the assets actually are. The AI cannot make these calls independently. This is the part of the collaboration that cannot be delegated, and recognizing that early changed how I thought about my role in the process.
CLAUDE.md setup felt like overhead — until Day 2 At the end of Day 1, spending time on CLAUDE.md and agent memory felt like admin work. The return came at the very first message of Day 2 — I opened with "can you read the plan from claude.md?" and got back the full Day 2 scope, conventions, and constraints with zero re-explanation. The investment compounds: every convention I add to CLAUDE.md now saves explanation in every future session. I'd make this a Day 1 habit for any multi-session project.
Day 2 — Learning to direct the tool
Category Observation
Understand before you approve Asking "what is a treemap?" before agreeing to build one, and requesting an ASCII mockup before Plan Mode, changed the quality of what I approved. I now treat "show me what this looks like" as a standard step before any visualization or layout decision. Building and then deciding you don't like it is far more expensive.
Injecting engineering philosophy as standing instructions Adding Strategy, Pipeline, Facade, Factory, Dependency Injection, and Registry to CLAUDE.md as standing instructions was the highest-leverage action of Day 2. One prompt permanently reshaped the codebase. The AI applied all 6 patterns correctly across 8 new files without further prompting. CLAUDE.md is not documentation — it is the AI's standing orders.
AI interprets words, not intent — read critically When I asked for a "blue/grey theme," the AI first proposed changing the risk bucket colors — technically a blue/grey palette, but wrong in context. I caught this before any code was written and corrected it. Reviewing AI proposals critically before approving them is not a sign of distrust — it is the job of the human in the loop.
Domain knowledge from other frameworks improves AI decisions Bringing my Angular/NgRx background into the Streamlit session state discussion produced a better architecture than if I had just accepted the AI's default. The AI mapped my mental model to what Streamlit can support rather than dismissing it. Cross-framework knowledge is an asset in AI-assisted development, not an obstacle.
Plan Mode before large refactors Using Plan Mode before the app.py refactor let me catch two things before any code was written: the Facade might grow too large (documented a decomposition path), and the session state approach needed rethinking. Both were addressed in the plan. This is now a default step before any change touching more than 3 files.
Skills: stop re-solving the same setup problem Adding a /run skill for the Streamlit launch command means future sessions don't waste time re-discovering the command or re-setting up PATH. Skills capture operational knowledge. CLAUDE.md captures architectural knowledge. Together they make the AI a consistent collaborator, not a tool you have to re-orient every session.
What I'd ask an instructor Areas where I'm less confident in my agentic AI usage and would value feedback:

1. CLAUDE.md scope — Am I putting the right things in CLAUDE.md vs. agent memory? Is there a cleaner separation?
2. Plan Mode frequency — I used it for the large refactor but not for smaller changes. What's the right threshold?
3. Feedback loops — I caught the theme misinterpretation and the session state issue myself. Are there techniques to make the AI surface those ambiguities proactively, before I have to?
Day 3 — Learning to plan deeper
Category Observation
Longer planning pays off more for AI features The Day 3 planning session was longer than Days 1 and 2 combined — and produced zero mid-implementation reversals. Every architectural choice (LangChain vs. SDK, DI pattern, streaming UX, session caching, key management, open-source safety) was decided and recorded before touching code. The implementation was mechanical execution of an agreed design. Planning time is not overhead — for AI features, it is the design work.
Tradeoffs are decisions, not problems Choosing LangChain over the Anthropic SDK meant accepting a real loss: Anthropic's server-side prompt caching. I made that choice consciously, with full understanding of what was being traded away and why portability was worth more for this project. Making tradeoffs deliberately — rather than defaulting to whatever the AI suggests first — is a skill that develops across sessions, not within one.
Open-source thinking changes design decisions I didn't start Day 3 thinking about GitHub audiences. But the "will others run this?" question changed the API key design, the secrets.toml.example approach, the visible-but-disabled pattern for the AI tab, and the planning docs structure. Asking "who else will use this and what will they see?" is a design question as much as a distribution one.
AI-assisted development is observable The three plan documents (docs/plan-day1.md through plan-day3.md) capture not just what was built, but how decisions were made — what was considered, what was rejected, and why. That record is only possible because planning happened through conversation with an AI that could preserve the reasoning. The artifact isn't just the app; it's the thinking trail behind it.
What I'd ask an instructor (Day 3 additions) 1. LangChain abstraction depth — Is LCEL the right level of abstraction for a project at this scale, or is it over-engineering for 2 insight types?
2. Planning docs as deliverables — Are docs/plan-dayN.md files a useful artifact for course submissions, or is prompts.md sufficient?
3. Streaming UX vs. simplicity — I chose streaming for the live feel. But for insights that take 2–3 seconds, does the UX benefit justify the added complexity?
